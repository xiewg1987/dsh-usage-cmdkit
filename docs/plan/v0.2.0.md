# v0.1.0 审核与 v0.2.0 计划

> 审核日期：2026-10-22  
> 审核对象：`dsh-usage-meters@0.1.0`（git 标签 `v0.1.0`，标签后仅一个 README 提交 `f211f95`）  
> 结论：**0.1.0 可以作为第一个公开版本，但面板的“时间窗口径”存在系统性错误，不适合直接在此基础上加功能。**  
> 下一步：先发一个很小的 `0.1.1` 热修，再以 **“数字可信”** 为主题做 `0.2.0`。

---

## 0. 一页结论

### 发布状态

| 项 | 状态 |
|---|---|
| git 标签 | `v0.1.0` 存在；标签后只有 `f211f95 docs(readme)` |
| npm（npmjs） | `latest = 0.1.0`，解包体积 398,815 B |
| 当前环境默认源 | `registry.npmmirror.com`，仍指向 `0.0.0-stage`，`0.1.0` 404 |
| 构建 | `pnpm run typecheck`、`pnpm run build:client` 均可通过 |
| 浏览器半产物 | `lib/client.js` **66,504 B**（README 写的 ≈34 KB 已过时） |
| 测试 / CI / CHANGELOG | **都没有** |

> 默认源的问题 README 已经用 `--registry=https://registry.npmjs.org/` 说明了，不是代码 bug；但它是安装支持的高频坑，发布后要持续确认镜像同步状态。

### 最严重的两个问题

1. **时间窗口径错位（P0）**：`byProvider` / `dailyByProvider` 永远按 30 日返回，但 Top、告警、宽版“按来源”卡在今日 / 7 日窗口下继续使用它们，却拿**所选窗口的总量**做分母。实测可出现“今日占比 390%”、Top 模型排错、峰值日错、告警文案写“近 7 日”但实际按 30 日算。
2. **多路由 turn 重复计数（P0）**：一个 turn 有多个 `routes`（重试 / fallback）时，`providerKeys()` 把**整轮用量**记到每一个 route 上。实测一轮 20 tokens、两个 route，`byProvider` 相加为 40。这个错误会持久化进 JSON，并污染后续所有窗口。

### 0.2.0 只做四件事

1. **窗口一致**：所有数字都明确属于今日 / 7 日 / 30 日中的同一个窗口，份额不超过 100%，标签不再撒谎。
2. **归因诚实**：单路由 turn 精确归因；多路由 turn 进入 `__mixed__` 桶，绝不重复计入；历史数据明确标注“可能含重复计数”。
3. **持久化抗坏**：坏 JSON 不拖垮面板；未来版本文件不被静默覆盖；写盘有备份 / 隔离 / 唯一临时文件。
4. **工程护栏**：纯函数测试、协议不变量测试、Windows + Linux CI、CHANGELOG 与协议文档同步。

**明确不做**：费用估算、命令面板 / 全局快捷键、3D、云同步、配置 UI、Top3 截断。这些不是 0.2.0 的主题，硬塞进来只会稀释“可信”。

### 2.3 P0-1：30 日 provider 拆分被当成所选窗口

**现象**

`UsageSummary.byProvider` 和 `dailyByProvider` 的契约是“近 30 日”（`protocol.ts:63-78`）。但面板把 `range` 切到今日 / 7 日时，只切换了总量 `buckets` 和 `total`，provider 列表仍来自 30 日：

```ts
// UsageDashboard.tsx:173-176
const providers = useMemo(
  () => summary?.byProvider ?? [],
  [summary],
)
```

随后这些 30 日 `providers` 被传进窄栏 / 宽栏：

```ts
// UsageDashboard.tsx:312 / 316 / 357 / 361
days={RANGE_DAYS[range]}
providers={providers}
```

下游全部按“当前窗口”解释：

- `UsageTopView.tsx:344-347`：每个模型的值来自 30 日；
- `:355`：`topShare = models[0].value / total`——分子 30 日、分母所选窗口；
- `:357`：`perModel = total / models.length`——总量是所选窗口、模型数是 30 日；
- `:359`：`modelHitRates(providers, total)`——份额分母错；
- `:368-371`：`peakDay` 从 30 日 `daily` 取，7 日 / 今日窗口下会取到窗口外的峰值；
- `UsageWide.tsx:373-390`：“按来源”卡同样用 30 日 `providers`；
- `UsageAlertsView.tsx:100-110`：`avg` / `peak` / `delta` 都基于 30 日 `daily`，但 `alerts.open` 和 `windowShort` 写的是所选窗口；
- `:106`：`lastDay` 取 `daily[daily.length - 1]`，永远是“今天”，不是“最近有记录的一天”。

**实测**

合成数据里今日 400、30 日 1560，Top 屏今日视图显示 `1560 / 400 = 390%`。`percentOf()`（`usage-theme.ts:183-186`）不做上限截断，所以 390% 会原样上屏。

**影响**

这不是“略微不准”，而是同一屏上的三个数字互相矛盾：总量是今日的，模型是 30 日的，百分比是两者相除。用户一旦发现一次，后面所有数字都不可信。

**修复方向**

新增纯函数，把“窗口切片”收口到一处：

```ts
// usage-metrics.ts
export function providersInWindow(
  dailyByProvider: readonly UsageProviderDaily[],
  days: number,
): UsageProviderTotal[]
```

- 对每个模型 `entry.daily.slice(-days)` 求和；
- 过滤全零模型；
- 按四桶总和降序；
- 保留 `__mixed__` / `unknown` 桶；
- 单测保证：`providersInWindow(dailyByProvider, 30)` 与 Host 的 `byProvider` 一致。

Dashboard 统一算一份 `windowProviders` / `windowDaily`，再传给窄栏、宽栏、Top、告警。Top 的“模型走向”是固定的 30 日视图，单独传 `dailyByProvider` 并在卡上明确写“30 日”，不要跟着所选窗口漂移。

**验收**

- 任意窗口下，`sum(windowProviders) <= total`；每个模型占比 ≤100%；
- 今日窗口的 `providersInWindow(..., 1)` 只包含今天有量的模型；
- 30 日窗口的 helper 结果与 `summary.byProvider` 逐项相等；
- 今日 / 7 日 / 30 日的 Top 头部占比、单模型均量、峰值日都使用同一个窗口。

### 2.4 P0-2：多路由 turn 整轮重复归因

**现象**

`usage-store.ts` 的归因逻辑：

```ts
function providerKeys(usage: TurnTokenUsage): string[] {
  if (usage.routes === undefined || usage.routes.length === 0) return ['unknown']
  const keys = new Set<string>()
  for (const r of usage.routes) keys.add(`${r.provider}/${r.model}`)
  return [...keys]
}
```

`mergeTurnIntoFile()` 随后把**整轮 `inc`** 加给每一个 key：

```ts
for (const pk of providerKeys(usage)) {
  const pPrev = day.byProvider[pk] ?? zeroBuckets()
  day.byProvider[pk] = addBuckets(pPrev, inc)
}
```

但 `@deepseek-ai/dsh-token-meter` 的类型说明写得很清楚：

> `TurnTokenUsageRoute`: One provider/model route that contributed a billed request attempt.
>
> `TurnTokenUsage`: Exact provider-reported token accounting for **every attempt** in one completed Turn.

也就是说 `routes` 是“这一轮里所有计费尝试涉及的路由”，token 是**所有尝试的合计**，并没有按 route 拆分的 token。当前代码把合计值复制给每个 route，等于把一轮的账记了 N 次。

**实测**

一轮 `total = 20`、两个 route（`a/x`、`b/y`）：

```text
sum(byProvider) = 40
```

这不是显示层问题，`persistTurnUsage` 会把它写进 `usage-stats.json`，之后所有窗口都错。

**修复方向**

不再假装能拆分。按以下规则归因：

| turn 的 routes | 归入 | 说明 |
|---|---|---|
| `undefined` / 空 | `unknown` | 无来源信息 |
| 去重后只有 1 个 | 该 `provider/model` | 精确 |
| 去重后 >1 个 | `__mixed__` | 多路由 / 重试 / fallback，整轮记一次，不拆 |

- 新增常量 `MIXED_PROVIDER = '__mixed__'`，UI 映射为“多路由（未拆分）”；
- 新增可选的 `attribution` 统计（`totalTurns` / `exactTurns` / `mixedTurns` / `unknownTurns`）；
- 对旧文件，`attribution` 缺失时视为 `legacy`，UI 明确提示“0.1 历史数据可能包含多路由重复计数”；
- 新数据必须满足不变量：`total === sum(byProvider)`（含 `__mixed__` / `unknown`）；
- 不尝试从旧文件反推，因为旧文件没有保留每轮 route 明细，反推一定是猜。

**关于“按 attempt 精确拆分”**

理论上可以自己 fold 每轮 attempt 的 usage 事件，拿到每个 route 的 token；但那等于在插件里复刻 `@deepseek-ai/dsh-token-meter` 的 fold 逻辑，风险和维护成本都高。0.2.0 不做；可以作为上游 `token-meter` 的 feature request：给 `TurnTokenUsage` 增加 per-route breakdown。等上游支持后再升级归因。

**验收**

- 单路由 turn：`sum(byProvider) === total`；
- 多路由 turn：`sum(byProvider) === total`，且出现 `__mixed__`，没有重复；
- 无 routes：进入 `unknown`，仍然满足等式；
- 旧文件读取不报错，`legacy` 标记可见；
- 单测覆盖 2 个 route、2 个相同 route、0 个 route、1 个 route。

### 2.5 P1-1：持久化在坏数据 / 版本变化前不够硬

**现状**

```ts
// usage-store.ts:147-165
try {
  const raw = await readFile(path, 'utf8')
  const parsed = JSON.parse(raw) as UsageStatsFile
  if (parsed.version !== FILE_VERSION || typeof parsed.days !== 'object') {
    return emptyFile(DEFAULT_RETENTION_DAYS)
  }
  return { ... }
} catch (error) {
  if ((error as NodeJS.ErrnoException).code === 'ENOENT') {
    return emptyFile(DEFAULT_RETENTION_DAYS)
  }
  throw error
}
```

问题：

1. **坏 JSON 直接抛**：`JSON.parse` 的 `SyntaxError` 没有被捕获，汇总路由返回 500，后续 `persistTurnUsage` 也继续失败。用户只能手动找到文件删掉。
2. **版本不符静默返回空**：`parsed.version !== FILE_VERSION` 时直接返回空文件，下一次写入会把原文件覆盖。用户看到的是“数据没了”，而且没有备份。
3. **没有隔离 / 备份**：坏文件、旧版本文件都没有被保留到可诊断的位置。
4. **固定 `.tmp`**：`writeStatsAtomic()` 用 `${path}.tmp`，两个进程同时写会互相踩；跨进程也没有锁（`writeChain` 只覆盖单进程）。
5. **retentionDays 未校验**：`Math.max(1, Math.trunc(file.retentionDays))` 遇到 `NaN` 会得到 `NaN`，`dayKeyOffset(now, NaN)` 产出无效日键。

**修复方向**

把“读”变成一个明确的结果类型，而不是“文件或抛错”：

```ts
type ReadOutcome =
  | { kind: 'ok'; file: UsageStatsFile }
  | { kind: 'missing'; file: UsageStatsFile }
  | { kind: 'recovered'; file: UsageStatsFile; quarantinePath: string }
  | { kind: 'unsupported'; foundVersion: number }
```

行为：

- `ENOENT` → `missing`，空文件；
- `SyntaxError` / 形状不合法 → 把原文件重命名为 `usage-stats.json.corrupt-<timestamp>`，返回 `recovered` + 空文件，并在日志与响应里留 warning；
- `version` 不是当前版本 → `unsupported`，**不写、不覆盖**；汇总路由返回带 warning 的空摘要（或 409），UI 显示“统计文件来自更高版本，请升级插件”；
- 写入前把当前文件备份为 `.bak`（至少在 clear / 首次修复写回时）；
- 临时文件改成 `${path}.${process.pid}.${random}.tmp`；
- `retentionDays` 校验为有限整数并夹在合理区间（如 1–3650），否则回退 30；
- 校验每个 day key 与四桶计数：非负安全整数，非法条目丢弃并记录数量。

**跨进程写入**

0.2.0 建议先**明确边界**：一个 profile 只允许一个 DSH Host 进程写。README 写清楚；如果确实要支持多进程，再上目录锁或 append-only JSONL。不要在 0.2.0 里同时做“归因重构 + 文件格式重构 + 跨进程锁”，风险叠加。

**验收**

- 手写一个 `{` 开头的坏文件：汇总不 500，原文件出现在 `.corrupt-*`，下一次写入成功；
- 手写 `version: 99`：不覆盖，UI 明确显示不兼容；
- `retentionDays: NaN` / `-1` / `1e9`：不产生无效日键，回退 / 夹紧；
- clear 前有 `.bak`，误清空可人工恢复；
- 单测覆盖上述分支（用 `mkdtemp`，不碰真实 profile）。

### 2.6 P1-2：稀疏数据把“安装前的零”当成真实零日

**告警**

`deriveAlerts()` 对完整 30 日 `daily` 求平均：

```ts
const totals = daily.map(...)
const avg = average(totals)
const peak = Math.max(...totals)
const peakOver = ((peak - avg) / avg) * 100
```

`daily` 是零填充的：安装前 20 天全是 0。平均被稀释，峰值自然显得很高，于是新用户第一天就会收到“单日用量触到窗口高点”。这不是“告警”，这是“安装日期提醒”。

**节律**

`deriveRhythm()` 同样把零填充日计入：

- `idleDays` 把安装前的 20 天算成“零日”；
- `weekendValues` / `weekdayValues` 把安装前的零日算进工作日平均，导致“周末 / 工作日”比例失真；
- `spread` / `volatility` 也被零日拉偏。

**修复方向**

- 所有基于日序列的统计先做 `trimLeadingZeros()`：从第一个 `total > 0` 的日开始；
- 观察天数不足时返回 `null`，UI 显示“样本不足”，不要硬算；
- 峰值告警要求窗口内至少 3 个观察日；7 日变化要求至少 14 个观察日（或明确标注“样本不足”）；
- `UsageRhythm` 增加 `observedDays`，UI 可以显示样本量；
- 今日窗口不做“峰值”告警（只有一天，没有“高于日均”可言）。

**验收**

- 只有 2 天数据的新安装：不产生峰值告警；节律的周末比 / 峰谷比为 `null`；
- 连续 30 天数据：统计与旧行为一致（除了修正后的零日口径）；
- 单测覆盖 1 天、2 天、7 天、14 天、30 天五种输入。

### 2.7 P1-3：今日涨跌是“半天 vs 全天”

`windowDelta(daily, 1)` 取今天和昨天各 1 天：

```ts
const recent = totals.slice(-1)      // 今天，可能只过了 3 小时
const previous = totals.slice(-2, -1) // 昨天，完整一天
```

上午打开面板，今日总量必然远低于昨天全天，涨跌签显示大幅负数。这不是趋势，是日历效应。

**修复方向**

- `days === 1` 时返回 `null`，UI 不画涨跌签（或显示“今日进行中”）；
- 如果将来想比较“昨日同期”，需要小时级 bucket；当前文件只有日粒度，不做假同期；
- `windowDelta` 返回 `{ percent, span }`，让标签的“较前 N 日”与实际比较跨度一致；
- 7 日：最近 7 日 vs 前 7 日；30 日：后 15 日 vs 前 15 日（保持现有设计，但标签写清楚）。

**验收**

- 今日窗口不出现负数涨跌签；
- 7 日 / 30 日窗口的 `span` 与标签一致；
- 前一窗口全零时返回 `null`，不画箭头。

### 2.8 P1-4：底栏状态在“撒谎”

`UsageDashboard.tsx` 里：

```ts
const footerStatus = `${t('footer.repo')} · ${t('footer.synced')} · ${t('footer.local')}`
```

无论 `status` 是 `loading` 还是 `failed`，都写“已同步 / 本机正常”。窄栏同样写死：

```ts
status={`${t('footer.synced')} · ${t('footer.local')}`}
```

宽版 / 窄栏的 `StatusFooter` 还都写死 `dot="ok"`（绿点）。读取失败时，面板上方有一行“无法读取用量”，底栏却显示绿色“已同步”。

另外 `UsageSummary.generatedAt` 从来没有上屏，用户无法判断看到的是 10 秒前还是 3 小时前的数据。

**修复方向**

- 底栏文案由 `status` 派生：
  - `loading` → “正在读取…”
  - `ready` → “已同步 · 更新于 HH:MM”
  - `failed` → “读取失败 · 上次成功 HH:MM”（没有成功过就“读取失败”）
- `dot` 由 `status` 派生：`ready` 绿点，其他灰点；
- `usage-state.ts` 记录 `lastSuccessAt`；失败时保留旧 `summary`，但明确标“stale”；
- `ensureUsageLoaded()` 的 `loaded` 只在成功后置位，失败后下次挂载允许重试；加一个最小重试间隔（如 30s）避免死循环；
- 可选：页面重新可见且数据超过 60s 时自动刷新（放 0.3.0 也行）。

**验收**

- 模拟 fetch 失败：底栏不显示“已同步”，绿点变灰，旧数据仍在但标 stale；
- 恢复后点刷新：状态回到 ready，显示新的更新时间；
- 首次失败后切走再切回：会再次尝试，而不是永远停在 failed。

### 2.9 P1-5：指标块的占比分母错

窄栏和宽版都有两枚固定指标块：

```tsx
<StatTile
  label={t('stat.today')}
  value={formatCompact(todayTotal)}
  share={total > 0 ? percentOf(todayTotal, total) : 0}
/>
<StatTile
  label={t('stat.d7')}
  value={formatCompact(d7Total)}
  share={total > 0 ? percentOf(d7Total, total) : 0}
/>
```

`total` 是所选窗口总量。选“今日”时，第二枚“近 7 日”的占比是 `d7 / today`，可以远大于 100%；选“7 日”时第一枚的占比是 `today / d7`，语义又变成“今天占 7 日的比例”，与“今日”标签并不匹配。

**修复方向（二选一，推荐 A）**

- **A. 固定分母**：两枚指标块永远表示“今日 / 近 7 日”，占比统一除以 `d30Total`，并在视觉上标明“占 30 日”（`sub` 或小标题）。简单、稳定、不会 >100%。
- **B. 动态语义**：指标块跟着窗口变（今日窗口显示“今日 / 昨日”，7 日窗口显示“今日 / 前 7 日”……）。信息更贴切，但文案、数据、布局都要跟着变，0.2.0 不值得。

**验收**

- 任意窗口下两枚指标块的占比都在 0–100%；
- 分母在 UI 上可解释（有“占 30 日”字样或等价说明）。

## 3. 做得好的地方

审核不是只挑毛病。以下决定建议在 0.2.0 里保持不变：

1. **Host / Client 分离干净**：`protocol.ts` 只有常量与类型，Client 不读盘、不 import Host 实现。
2. **本地优先**：统计文件在 DSH profile 下，经认证路由读回，没有遥测上报、账号、后端。
3. **不重复造 token 口径**：直接复用 `dsh-token-meter` 的四桶，不做第二套估算。
4. **不做费用估算**：费率会变、合同价因人而异，面板只报 token。这个取舍是对的，0.2.0 不要加回来。
5. **不占全局快捷键**：`⌘K` / `⌘/` 的冲突判断正确；面板内操作留在面板内。
6. **`TAB_KIND` 稳定**：`usage-dashboard` 不改名，避免已打开 Tab 失效。
7. **原子写 + 单进程串行**：`tmp` + `rename` 与 `writeChain` 是正确方向，0.2.0 是在这个基础上加固，不是推翻。
8. **协议校验器**：Client 不信任响应体，形状不符就当失败，这个原则很好；0.2.0 把不变量补齐即可。
9. **设计稿与实现同源**：v6 预览是真实组件渲染，不是另画静态图；这套流程值得保留。
10. **发布包透明**：`files` 包含 `src`、`docs`、构建脚本，55 个文件、398 KB，便于审查。

## 5. v0.2.0 计划：数字可信

### 5.1 主题与目标

一句话：**同一屏上的每个数字，都能用同一句话解释它是哪个窗口、怎么算出来的；坏文件不拖垮面板，历史数据不假装精确。**

## 6. v0.3.0 候选（不进 0.2.0）

按优先级：

1. **配置**：`storagePath`、`retentionDays`（README 已列“计划中”）。需要 Schema + Configure 或面板内编辑；先定义“配置改变后旧文件怎么办”。
2. **Top3 + 展开**：默认显示前 3，提供“显示全部”。不要默认藏数据。
3. **导出**：CSV / JSON（按日、按模型），方便用户自己分析；仍然只导 token，不导费用。
4. **自动刷新**：页面重新可见且数据超过 60s 时刷新；可配置关闭。
5. **跨进程写入**：目录锁或 append-only JSONL + 定期 compaction；只有在确认多 Host 进程是真实场景后再做。
6. **上游 per-route breakdown**：向 `dsh-token-meter` 提 feature request，拿到每个 attempt 的 token 后再做精确路由归因。
7. **DSH 兼容矩阵**：把当前钉死的 `0.2.1-alpha.1` 与未来版本做成表；升级 DSH 时按表改 `dependencies`。
8. **lint / format**：ESLint + Prettier 或 Biome；0.2.0 先把 `noUnusedLocals` 和测试跑起来。

### 7.3 合成数据脚本（关键断言）

```js
// 30 日：今天 400，其余每天 10；byProvider 只有一个模型，30 日合计 1560
const s = summarize(file, now)
// s.today = 400, s.d7 = 640, s.d30 = 1560
// s.byProvider[0] = 1560  -> 今日视图若直接相除 = 390%

// 一轮 20 tokens，两个 route
await persistTurnUsage({ ..., routes: [{ provider: 'a', model: 'x' }, { provider: 'b', model: 'y' }] }, now, path)
// 当前：byProvider = { 'a/x': 20, 'b/y': 20 } -> sum = 40
// 目标：byProvider = { '__mixed__': 20 } -> sum = 20
```

### 7.4 `pnpm install` 失败原文

```text
[ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: esbuild@0.28.1

Run "pnpm approve-builds" to pick which dependencies should be allowed to run scripts.
```

根因：pnpm 11.9 的包级放行键是 `allowBuilds`，不是 `onlyBuiltDependencies`；旧键被忽略，pnpm 还会往 `pnpm-workspace.yaml` 写 `allowBuilds: esbuild: set this to true or false` 占位。改成 `allowBuilds: esbuild: true` 后安装通过。

## 8. 总结

0.1.0 的**结构**是健康的：Host / Client 分离、本地优先、四桶口径复用、原子写、协议校验、设计稿同源，这些都值得保留。问题集中在**“窗口”与“归因”两个语义层**：数据本身在盘上是对的，但面板把 30 日的拆分套进了今日 / 7 日的分母；多路由 turn 又把整轮账记了多次。

0.2.0 不需要新功能，只需要把这两个语义修到“可对账”，再把坏文件、状态显示、测试与 CI 补齐。做完之后，这个面板才真正配得上“用量遥测”这四个字。
