## 2. 视觉系统（v6 的硬规矩）

### 2.1 色

| 角色 | 值 | 用在哪 |
|---|---|---|
| 面板底 | `#070a12` | 整个面板 |
| 卡片底 | `rgba(255,255,255,.035)` | 所有卡片 |
| 卡片描边 | `rgba(255,255,255,.06)`，1px INSIDE | 所有卡片 |
| 发丝线 | `rgba(255,255,255,.07)`，1px | 分隔线、进度条轨道 |
| 主强调 | `#38bdf8` | 选中态、进度、聚焦环 |
| 品类梯队 | `#38bdf8` / `#38bdf8c7` / `#38bdf894` / `#38bdf86b` | 竖屏四行遥测的圆点、微折线、细条（同一色相的四档亮度） |
| 正向 | `#22c55e` | delta 上涨、命中率副值（**宽版**） |
| 负向 | `#ef4444` | delta 下跌（只在有负值时出现） |
| 主文本 | `#f2f5f9` | 数值 |
| 次文本 | `#8b94a3` | 标签、说明 |
| 三级文本 | `#5b6472` | 脚注、版本号 |

**强调色上限 = 2**（蓝青 + 涨跌绿/红）。品类色（未缓存/输出/缓存读/缓存写）
只允许出现在**圆点与细条**上，百分比一律灰阶——这条 v5.1 已经做对，保留。

**竖屏那一版再收一档：整屏只有一种彩色。**
四个桶并排出现时，四种色相（蓝 / 绿 / 紫 / 橙）会把四行读成**四件事**；
它们其实是同一份用量的四个切面，所以竖屏改用**同一色相的四档亮度**
（`BUCKET_RAMP`），涨跌签、指标条、洞察条也一律走界面蓝青——
竖屏一屏里不再出现第二种色相。**宽版不动**：它的主环本来就是四段桶色弧
（见 §9.5），列表再四色就太吵，宽版列表仍用四色玻璃（`palette="glass"`）。

### 2.2 字

- 数字：Inter，`font-variant-numeric: tabular-nums`，字重 600–700。
- 标签：JetBrains Mono 或 Inter，9–10px，字距 `0.12em`，全大写。
- 中文标签用 Inter（不套字距，中文全大写会散）。

| 级别 | 字号 | 字重 | 用途 |
|---|---|---|---|
| 大数 | 40–44 | 700 | 总 tokens |
| 指标数 | 22–24 | 700 | 命中率等 stat |
| 正文 | 13 | 500 | 分类行名、洞察正文 |
| 标签 | 10 | 500 | 卡片标签、药丸 |
| 脚注 | 9 | 400 | 版本号、同步时刻 |

### 2.3 间距与形状

- 间距刻度 **4 的倍数**：4 / 8 / 12 / 16 / 20 / 24。
- 卡片圆角 **12**（大卡）/ **10**（小卡）；面板圆角 14。
- 卡片内边距：主指标卡 16，四行列表卡 14×14，stat 卡 12×13。
- 卡片之间垂直间距：**12**（密）或 **16**（疏）；同一组内 8。
- 行高：分类行 **44**；stat 卡高 **64–72**；药丸高 **24**（紧凑 20）。

## 4. 竖屏 360×800 新版面骨架

从上到下的**密度节奏**：上密（头 / 控件 / 主指标 / stat）→ 中疏（分类列表）→ 收口（洞察 / 状态条）。

| 区块 | 高度 | 关键变化（相对 v5.1） |
|---|---|---|
| 品牌头 | 44 | 左侧 `DSH CmdKit` 16px，右侧 `Usage` 9px 灰字 |
| 分隔线 | 1 | 发丝线 |
| 控件行 | 32 | 视图 Tab 改成 **SegmentedControl**（暗底容器），时间窗药丸右对齐 |
| 主指标 | 150 | 大数 44 + **DeltaChip** + **Sparkline 120×24**；右侧 `MiniGauge 72` 改表**命中率** |
| stat 行 | 72 | **两枚横排**（命中率 / 缓存读比），不再是单枚高卡 |
| 分类列表 | 204 | 4 行 × 44，行内加**微型 sparkline**；行间发丝线 |
| 洞察卡 | 72 | 小标题 + 两行正文 + 右侧占比条 |
| 弹性空隙 | 余量 | 上密下疏的留白落在这里 |
| 状态条 | 24 | 绿点 + `dsh-usage-cmdkit · synced · local ok` + 版本号 + ghost 按钮 |

合计约 **660px + 间距**，落在 800 里余 ~90px 呼吸——**留白集中在下半段**，
这是与 v5.1「上中下均匀、底部一大块空」最大的差别。

## 5. v5.1 现在为什么还是不好看

对着上面的参考逐条比，v5.1 那版（金融竖屏）的问题：

1. **一枚指标卡占满整行还 95px 高** —— 一个数字浮在中间，空白比信息多。
   参考里这一层永远是「两枚 stat」或「stat + delta」。
2. **右侧 64px 环信息量低且重复** —— 它表示「未缓存输入占比 38%」，
   而下面列表第一行已经写了 38%。参考里的环通常表达一个**别处没有的量**
   （命中率、进度），建议改成命中率环。
3. **大数下面只有「日均 24.8K」一行字，没有趋势** —— 参考里大数正下方是
   delta chip 或 sparkline。我们有日数据却没画出来。
4. **分类行只有圆点+条+数字，看不出波动** —— 参考里每行右侧带一段微型 sparkline。
5. **洞察卡是纯文字一段** —— 参考里是「小标题 + 说明 + 占比条」三层。
6. **顶部两套控件打架** —— `OVERVIEW/TOP/ALERTS` 用下划线选中态，
   时间窗用实心蓝药丸，两个选中语言放在一行很吵。改成暗底分段容器 + 描边药丸。
7. **状态条没有状态点** —— 刷新/清空按钮与状态文字都是小字，缺一个「活着」的信号。
8. **卡片内文字偏贴边** —— 内边距 12–14 在 360 宽下显得挤，行高应到 44。
9. **密度均匀** —— 上中下一样松。金融竖屏是**上密下疏**。

## 9. 实施后记（这一轮踩到的东西）

### 9.1 方案本身的两处矛盾与取舍

1. **§4 的 stat 行（命中率 / 缓存读比）与 §5.2 的「环改成命中率」重复了。**
   同一件事在环与 stat 里各说一遍，就是两处信息冗余。
   取法：环讲**别处没有的量**（命中率），stat 改成两个时间尺度的**总量**
   （TODAY / 7 DAYS + 各自占 30 日的比例）。
2. **§4 的控件行 32px 装不下。** `SegmentedControl` 与长短版时间窗药丸
   在 360 宽下合计 ≈341px > 可用的 328px，硬塞会把字压到 8px 以下。
   取法：时间窗改用**短档位** `TODAY / 7D / 30D`（≈103px），
   合计 ≈292px，一行放下，还省下 28px 的竖向空间。

### 9.2 实现层

- **趋势数据没有新开通路**：`UsageSummary` 加 `daily`（30 日、零填充、旧→新），
  折线 / 行内微折线 / 涨跌签都从这一份来。
- **涨跌签要比就比真的**：当前窗口日均 vs 前一等长窗口日均；
  30 日窗退化成后 15 天 vs 前 15 天；**凑不出数据就不画**。
- **组件的 `children` 必须从 props 取**（见 README「实现要点」里的 React 坑）——
  写成第二个位置参数会拿到 legacy context，图标直接炸。
- **底栏按钮带图标，但不省文字**：刷新 ↻ / 清空 🗑 各配一枚 11px Lucide 图标，
  文字标签保留——「清空」不可撤销，光一个垃圾桶认不出会点到什么。
  图标让两枚按钮各宽 15px（图标 11 + 间隙 4），整组仍右对齐到面板右缘。

### 9.3 工具层

- **Figma 的 `batch` 时灵时不灵**：插件 0.6.0 本身传数字没问题（坐标、颜色、圆角都精确回写），
  竖屏 360×800 的稿子靠它几批就搭完。但宽版这条链路上 `batch` **把所有数字参数转成了字符串**
  （报「expected number, received string」，数组参数变 object）。
  绕法：**脚本生成一份整帧 SVG → 一次 `import_svg`**（`make-figma-frame.mjs`）。
- **Figma 的 `set_fills` 不接受空数组**：`fills: []` 会被当成字符串而报错，
  「透明」要写成 `opacity: 0` 的实色。
- **SVG 的 `stroke-dasharray` 进 Figma 会散成多段断弧**；
  环形的进度要用 Figma 原生弧形（`set_arc`）画。
- **SVG 的 CSS `transform` Figma 不认**，要烘焙成 SVG 属性。
- **SVG 的 `viewBox` 不能剥**：里面的路径用的是 viewBox 坐标，不是元素像素。
  Lucide 图标的 viewBox 是 24×24，实际只画 10×10（11×11）——
  剥掉 viewBox 就按 24×24 画了，图标大一倍多，描边也跟着粗，
  结果是箭头压在涨跌签的文字上。整帧 SVG 里要显式写 `scale()`。
- **`text-transform: uppercase` 是 CSS 算出来的效果，DOM 里存的是原文**：
  不在导出的几何里带上 `textTransform`、也不在拼 SVG 时补 `toUpperCase()`，
  Figma 那边就是「Input (uncached)」而不是「INPUT (UNCACHED)」。

### 9.4 宽版这一轮（1280×720）

- **宽版是独立组件，不是「把竖屏拉宽」**：`UsageWideView` 与 `UsageCompactView` 同构，
  `UsageDashboard.tsx` 只负责量宽度、选布局、传参。
  预览要渲「真组件」，预览入口就得挂同一个组件——
  所以宽版也拆出了自己的 `design/_v6_src/preview-1280.tsx`。
- **环的大小是量出来的**：宿主右栏高度随窗口变（1080p 约 950，笔记本 750 上下）。
  固定尺寸定不了这件事。做法是「内容溢出多少就把环压小多少」，**只压不放**——
  放回去容易来回抖。1280×720 这一稿量出 41px 溢出，环压到 259。
- **窄宽共用的东西要抽出去**：折线序列与涨跌签的算法（`usage-metrics.ts`）、
  底栏 ghost 按钮的样式（`usage-buttons.ts`，预览与实现共用一份，
  否则成图里的按钮和真面板里的按钮会长得不一样）。
- **旧稿该清就清**：Figma 上 v5 的宽版双栏、金融竖屏、400×520 / 720×420 三张旧稿
  与它们所在的旧页一并删掉；仓库里 v5 的成图与预览说明也删掉，
  引用它们的 README 与 `motion-spec.md` 同步改指 v6。

### 9.5 拿掉 3D（2026-10-21 补记）

- **3D 轨道矩阵整个拿掉了**：`usage-3d.ts`（three.js 场景）、`UsageRing3D.tsx`、
  `scripts/render-design-ring.mjs` 与那 6 张环渲染资产全部删除，
  `three` / `@types/three` 也不再是依赖——浏览器半回到**一个产物**（≈39 KB）。
- **理由不是「不好」，是代价大于收益**：
  透视没法转矢量，设计稿里只能放位图，稿子与实现就不同源了；
  510KB 的 three.js 要么进首屏（首屏 +500KB），要么拆按需分片（多一套宿主机制）；
  而窄栏里一枚 3D 环既占地方又吵。
- **宽版改用扁平环放大**（`UsageRing.tsx`，259×259）。
  共享的是「弧 + 环心读数」这套**构件**语言——**配色并不共享**：
  宽版是四段桶色弧（蓝→绿→紫→橙），
  窄栏右侧的命中率表盘是**单色**青弧。
  顺带把 `UsageRing` 的 `variant` 机制也拆了——
  只剩一个调用方，两套形态参数留着就是死代码。
- **宽版主环与 §6 的张力：已定，走「保留四色、压掉 bloom」。**
  §6 明确不要「霓虹多色大环、四段彩虹环」，
  而这枚 259px 的四色环原本带着一圈彩色 bloom（`drop-shadow` 外发光）+
  环心两层柔光球，正好落在那条线上（窄栏没有这个问题）。
  做法：**弧上只留色、不留光**——
  去掉弧的 `drop-shadow`、去掉环心的 halo 与能量核（连带 4s 柔光呼吸），
  弧的玻璃渐变与镜面高光保留（那是明暗，不是发光）。
  四色不降：四色落在**环段**上是 v6 令牌规矩允许的位置
  （`usage-theme.ts`：四色只出现在环段、圆点、细条与图例），
  砍掉四色等于砍掉「哪段是哪个桶」这层对应关系。
  环外那四个百分比同时改回**灰阶**——窄栏的分类行百分比本来就是灰的。
  代价：环上没有常驻动画了，静止期只剩底栏状态点那一下微动（`motion-spec.md` §0）。
- **好处在设计稿这边**：环是纯 SVG，`PREVIEW_SVG=1` 直接导出，
  整帧 SVG 一次 `import_svg` 进去，**再没有位图**。

### 9.6 竖屏拆成三屏 + 一态骨架（2026-10-21 补记）

这一轮的成图不再是「一屏」，是**三屏 + 一态骨架**：总览 / Top / 告警，
外加读数时的骨架。改动落在实现上，稿子从实现导出（§7、§8 的老规矩没变）。

- **顶部分段控件原来只是装饰**：`SegmentedControl` 里三个 Tab 除了第一个都被
  `disabled`，点了没反应。现在它是真开关——
  `UsageDashboard` 持有 `view` 状态，竖屏与宽版共用（面板在两种构图之间换时，
  用户看的还是同一屏）。
- **头抽成 `UsageHeader`**：品牌行 + 发丝线 + 控件行（视图分段 + 时间窗药丸）。
  三屏换的是身体，头永远一样——来回切的时候头不该跳一下。
  宽版也改用它，两种构图的控件行从此同源。
- **选中态改成描边**：分段控件里选中项原来是「浅色实心药丸」，
  右边时间窗药丸也是实心，两处并排时选中语言打架。
  现在统一成**描边 = 选中**（冷青描边 + 冷青字）。
- **Top 屏**（`UsageTopView`）：头部模型的份额环（`TOP SHARE`）+
  三枚指标块（单模型均量 / 峰值日 / 缓存命中）+ `BY MODEL` 排行 + `BY PROVIDER` 汇总。
  环上的百分比是**头部模型占窗口总量**的份额——行里写这个模型的量，
  环里写它的权重，两处不重复。
- **告警屏**（`UsageAlertsView`）：告警**不是写死的**，
  是 `usage-alerts.ts` 从日序列与四桶用量里推出来的（峰值、占比爬升、增速掉队）。
  阈值集中在 `THRESHOLD` 一处；**不满足就不报**——面板只报 token，
  假装有事比说「这段时间没有异常用量」更糟。
- **骨架态**（`UsageSkeleton`）：读数时身体换成骨架，头与底栏照旧（底栏按钮此时仍然可用）。
  骨架分两种灰度：**块白 5% / 条白 15%**。
  条必须比块亮一档——骨架的全部信息量都在「条在不在」上；
  两者同亮度时整屏糊成一块灰板，缩略图与低亮度屏幕上读不出「在加载」。
- **竖屏整屏收成一种彩色**：四行遥测改用同一色相的四档亮度（`BUCKET_RAMP`），
  涨跌签、指标条、洞察条一律走界面蓝青。宽版列表仍是四色玻璃（`palette="glass"`），
  它的主环本来就是四段桶色弧（§9.5）。

### 9.7 补两组统计：分模型命中率与节律（2026-10-22 补记）

§9.6 那一轮把竖屏拆成三屏，三屏各自的版面都排满了。
这一轮**不加新块**，而是加两组已经在数据里、只是没被用起来的统计。

- **分模型命中率**（Top 屏）：`UsageSummary.byProvider` 的每一项**本来就带着完整四桶**，
  全局命中率是加权平均——量大的模型说了算，
  但「扛着 30% 的量却命中最低」的那个模型才是该修的。
  `usage-metrics.ts` 的 `modelHitRates()` 把它派生出来：
  竖屏并进 `BY MODEL` 排行做一列（`layout="compact"`），
  宽版独立成 `CACHE HIT` 卡（条上压一根全局命中率的竖线，看谁在线的下面）。
- **节律**（告警屏）：`usage-rhythm.ts` 的 `deriveRhythm()` 从 30 日序列推
  周末/工作日的日均比、连续活跃天数与零日天数、峰谷比（峰值÷中位数）与变异系数。
  峰谷比用**中位数**：平均数会被峰值自己拉高，拿它当分母算出来的比值偏小。
  竖屏挤进「每日总量」卡末尾一行（`variant="strip"`），
  宽版独立成 `RHYTHM` 卡（`variant="card"`）。

**一条新的版面规矩：窄屏塞进去，宽版独立成卡。**

360×800 的竖屏一屏只装得下这么多——总览屏余量只有 30px，
顶部分段 + 三屏 + 骨架已经是上限。所以同一组信息在两种构图里密度不同：
窄屏是**挤进已有的卡**（多一列、多一行），宽版是**独立成卡**。
跟 `UsageTelemetry` 的 `flat` / `wide` 是同一个做法，规矩也照抄那条。

三屏的成图高度都核对过：`contentHeight === clientHeight === 768`，一屏装得下，不切不裁。

**顺带修掉的排序口径**：`byProvider` 以前按 `未缓存输入 + 输出` 排序，
但排行行显示的量、TOP SHARE 环算的占比**都是四桶之和**——
排序依据和显示值不是一回事，缓存命中极高的模型会被排到后面，环里算的却不是它。
现已统一成四桶排序。

**还有一处 mock 的坑**：预览用的 `mock.ts` 原来用 `(index + 3) % 7` 判周末，
与真实日键**错位两天**，低位日落在周二/周四而不是周六/日。
已改成从当天日期自己算星期——这条对「工作日 vs 周末」这类统计是前提，
错了预览里算出来的东西就是假的。

### 9.8 补第三组统计：模型走向（2026-10-22 补记）

前两组统计（§9.7）都是**面板端派生**的——数据早就在手上，只是不用。
这一组要动宿主接口，但**同样不迁数据、不改文件格式**。

- **协议加一个字段**：`UsageSummary.dailyByProvider`——
  每个 provider/model 的 30 日四桶。
  宿主的 `DayRollup.byProvider` **每天每模型都存着四桶**，
  只是 `summarize()` 把它压成了一份 30 日合计。
  现在把它按模型、按天摊开，顺序与 `byProvider` 一一对应
  （同一个模型在同一位置，否则「排行第 2 的模型」和「日序列第 2 条」会错位）。
- **份额变化**（`modelShareShift`）：近 7 日的份额 vs 前 7 日的份额。
  份额是**相对**的——一个模型涨份额，别的必然让出；
  总量同时在涨的模型份额变化会被稀释，那不是「它在退」而是「大家都在涨」。
  两边都得有用量才比得了：前 7 日一点用量都没有时，
  「份额」无从谈起，算出来的 +100 是假数——**比不出来就返回 null**。
- **窄屏换卡**：Top 屏窄版原来有「按来源」卡，
  它那两行是模型行按 provider 求和的结果，模型名里本来就带着 provider，
  信息是重复的。换成「模型走向」卡（每行 = 名称 + 30 日微折线 + 份额变化），
  位置给**新的一维**更值。宽版放得下，两张都留。

**又一条版面规矩浮出来了**：窄屏一屏只装得下**两张**卡（Top 屏），
所以新统计进来时，要先看看哪张卡的信息是**重复的**，让位给它。

### 9.9 设计稿不许落后：ArtCraft 稿也走「实现导出」这条线（2026-10-22 补记）

这一轮把设计稿同步了一遍，发现它**落后了好几轮**：
`DSH CmdKit · Usage 360×800 (MCP)` 里的 Top 屏还是「TOP SOURCES · 30D」那版
（只有排行卡 + 摘要卡），实现上早就有的大数字、环、三小卡、分模型命中率、
模型走向，稿子里一样都没有。

**根源是流程**：稿子是「照着成图手摆」的。
成图会变，稿子不会跟着变——每加一轮统计，差距就大一分。
等到发现时已经差了好几轮，补是补不过来的，只能重搭。

**规矩**：设计稿**必须**从实现导出，不能手摆。
- 几何用 `PREVIEW_DUMP=1` 导（每个元素的盒子、字号、字重、颜色、字距、
  以及文字**自己的**渲染盒）；
- 矢量用 `PREVIEW_SVG=1` 导（实现里真正画出来的那份 SVG，不在稿子里重画）；
- 稿子用**原生节点**搭（文字仍是文字，图层带语义名），
  不走整帧 `import_svg`——那样文字全变路径，一个字都改不了。

跑法与踩过的坑见 [design/v6-preview.md](v6-preview.md) 的「ArtCraft 稿也走同一条线」。

**顺带一条**：改实现 → 重跑脚本 → 稿子重搭。
这条线通了以后，「设计稿不同步」就不该再是一个能攒好几轮的问题。
